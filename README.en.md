# TideWeave

**An embeddable event-time window engine aligned with Apache Flink's windowing model, plus the correction and retraction semantics Flink itself handles poorly.**

A MoonBit event-time windowing and correction-log engine. Late events merge sessions; retracting a bridge event splits them again. Every atomic correction emits a before/after changelog, an explicit watermark protects finalized facts, and a downstream view checks version continuity and stale before-images.

[Live laboratory](https://lmk-ai-nb.github.io/TideWeave/) · [Chinese README](README.md) · [Flink mapping](docs/FLINK_MAPPING.md) · [Semantics](docs/SEMANTICS.md) · [Protocol](docs/FORMAT.md)

## A concrete problem

Two records at 0 and 16 with gap 10 form separate sessions. A late record at 8 merges them; retracting that record splits them again. Subtracting a number from a stale SUM leaves wrong boundaries, members and min/max. TideWeave treats every correction as an atomic state change: compute candidate facts, rebuild affected keys, validate finality, commit a version and emit the full before/after changelog. A failed transaction leaves windows, indexes, dedup state and versions untouched.

## Implemented

- Tumbling, phase-offset sliding and session windows; half-open intervals; mathematical floor alignment for negative starts.
- Insert, replace and retract by event ID; cross-key moves; multi-mutation atomic transactions.
- Session late-merge and retraction-split; count / Int64 sum / min / max and full member provenance.
- Explicit watermark advancement and allowed-lateness tolerance; `WatermarkTracker` for bounded-out-of-orderness watermark generation; `within_lateness` probe.
- Pluggable custom aggregation (UDAF): `Measure` + `measure_window`, with built-in count/sum/min/max/avg.
- Configurable trigger: `Watermark` or `Count(n)` early firing; before/after changelog output guarded by the downstream `View`.
- Explicit state cleanup: `Forget` freezes finalized facts, frees active capacity, rejects later corrections, and replays deterministically through checkpoints.
- open → closing → final; finalized windows and their member facts are protected from reopening.
- Success-command idempotency and conflict detection; replayable checkpoint recovery preserving dedup.
- Deterministically ordered before/after changelogs; a downstream `View` that validates version continuity, before-images and atomic application.
- Strict JSON: duplicate decoded keys, unknown fields, fractional-token rounding and inapplicable parameters are rejected.
- Node CLI, three reproducible scenarios, an interactive browser laboratory, all sharing the MoonBit core.

See [Flink mapping](docs/FLINK_MAPPING.md) for a line-by-line mapping against Apache Flink's event-time windowing capabilities.

## Using from MoonBit

Requires MoonBit compiler 0.10.16+.

```sh
moon add LMK-ai-nb/tideweave@0.2.2
```

```moonbit
import { "LMK-ai-nb/tideweave" @tide }

let cfg = @tide.config(@tide.Session(gap=10), lateness=20)
let engine = @tide.Engine::new(cfg)
let view = @tide.View::new()
let outcome = engine.apply(@tide.Transact(id="batch-1", changes=[
  @tide.Put({ id: "left", key: "device-A", at: 0, value: 20 }),
  @tide.Put({ id: "right", key: "device-A", at: 16, value: 35 }),
]))
view.apply(outcome)
let restored = @tide.restore(engine.checkpoint())
assert_true(restored.rows() == engine.rows())
```

The full public interface is generated by `moon info` (see [pkg.generated.mbti](pkg.generated.mbti)). `aggregate` batches; `Engine` accepts corrections within capacity; `replay_json` / `resume_json` provide strict text boundaries.

## Relationship to existing MoonBit packages

August reviews rejected several submissions for overlapping with existing projects without disclosing the relationship. This project discloses the search results up front — see [Prior art](docs/PRIOR_ART.md).

Related MoonBit packages each have a distinct role: `moonwatermarkkit` provides watermark decisions and window assignment primitives (no stateful aggregation, no retraction); `moon-stream-quality` is a streaming data-quality rule engine with late-event policies; `moon-distinct-sketch` provides approximate sketches over bounded windows; `mooncep` performs complex-event pattern detection and explicitly does not support event corrections or retractions.

TideWeave shares no code with them and is not a fork, rename or extension of any of them; window assignment, watermark advancement, aggregation, correction and checkpoints are implemented independently. The difference concentrates in the correction layer: session rebuild after retraction, atomic multi-event transactions, finality protection and before-image validation. If you only need watermark decisions or data-quality rules, those dedicated packages are a better fit; if you need "a corrected fact must leave the windows consistent", use TideWeave.

## Two integration paths, no rewrite required

1. **Embed as a library**: `moon add LMK-ai-nb/tideweave` and call `Engine::apply` from MoonBit.
2. **Drive it as a pipeline**: `stream` consumes newline-delimited JSON (first line config, one command per later line) and emits one outcome per line plus a final summary and checkpoint. Any line-oriented producer — shell, `jq`, a Kafka consumer script, Python — can drive it directly:

```sh
cat examples/session-stream.ndjson | node bin/tideweave.mjs stream
node bin/tideweave.mjs stream examples/session-stream.ndjson --checkpoint saved.json
```

The same core backs the typed MoonBit API, the strict JSON protocol, the CLI and the browser laboratory. See [HOST_GUIDE.md](docs/HOST_GUIDE.md) for host-side examples.

## Why not just use Flink

Flink is a distributed cluster runtime for large, long-running, multi-tenant streams. TideWeave addresses a different problem: **when an already-recorded fact is corrected, how do you produce a verifiable, replayable correction the downstream can check?**

| Scenario | Flink's usual approach | TideWeave |
| --- | --- | --- |
| Session boundary after retracting a bridge event | retract stream left to downstream; boundaries not re-split automatically | rebuilds connected components, emits full delete + upsert |
| Finalized window rewritten by late data | relies on allowed lateness and downstream idempotency | final windows and member facts explicitly protected, even for equal sums |
| Downstream misses or holds a stale value | build your own version check | `View` atomically validates version continuity, before-image and row identity |
| Deployment | JVM cluster, state backend, checkpoint storage | single-process embeddable, deterministic replay, no external dependency |

Every Flink windowing primitive here is implemented to parity; the correction/retraction rebuild, finality protection and downstream validation are the independent contribution. The two operate at different deployment layers rather than replacing each other.

## Quality and boundaries

61 MoonBit tests include an independent interval-enumeration oracle, an independent graph-connectivity oracle, mixed-key state diffs, atomic rollback, finality protection, checkpoint recovery, custom aggregation, watermark generation, trigger and state freezing. 10 Node integration tests cover the public protocol and real CLI; Chromium checks interaction, export, injected text and a 390px phone layout. GitHub CI checks wasm, wasm-gc, js and native on Linux, macOS and Windows.

This is a **bounded, synchronous, single-process** embeddable state machine for offline reconciliation, edge batches and stream-processing regression fixtures. At most 5000 active events, 10000 successful commands, 20000 windows, 2 Mi canonical journal units. State cleanup is explicit: `Forget` freezes finalized facts and frees active capacity; frozen facts become replayable immutable history — never silently evicted. Continuous unbounded streams require the host to design partition/batch lifecycles; the host also owns message IO, persistence, authorization and external consumption consistency. There is no distributed runtime and no external exactly-once guarantee.

Windows/Node 24 synthetic benchmark: 4096 events, 64 keys, 32 batches, including parsing, correction, logging, checkpoint and full JSON output — median ~84 ms over 10 samples. See [BENCHMARK.md](docs/BENCHMARK.md) for environment, scope and reproduction; do not extrapolate to production throughput.
